# Ask First 发布打法

## 一句话定位

**别让 Agent 自信满满地做错东西。** Ask First 让 DSH 先查、再问、确认后开工。

对外不要把它讲成“又一个 prompt 插件”，而要讲成一个可见的行为改变：AI 不再把未知项悄悄变成代码。

## 已有方案与差异

| 类型 | 已有价值 | Ask First 的区别 |
| --- | --- | --- |
| DSH 原生 `ask_user_question` | 提供弹窗和结构化答案 | 原生层不判断何时问、问什么、何时已足够清楚。 |
| `oh-my-deepseek-harness` 的 `deep-interview` | 大型工作流技能包中的深度访谈 | Ask First 是独立、轻量、安装后自适应生效的默认行为。 |
| `SpecWorkflow` / `dsh-specflow` | 完整规格、工件和交付流程 | Ask First 不要求用户进入重型 spec 流程，只生成与任务成比例的 brief。 |
| `dsh-crew` | PM 加多角色团队的完整交付管理 | Ask First 不引入多 Agent 编排，专注在开工前的意图对齐。 |
| `dsh-prompt-enhance` | 在输入框里重写一次用户 prompt | Ask First 用多轮答案逐步收敛，不会在没有用户回答时补出需求。 |

不攻击这些项目。它们解决的问题更大；Ask First 的机会是成为“所有人默认都愿意开着”的小插件。

## 30 秒演示脚本

1. 在干净的 DSH Web 中输入：“帮我做一个轻量 CRM。”
2. 展示 Agent 先检查仓库，然后弹出 1–3 个原生决策题，每题有推荐和取舍。
3. 选择一个会导致方案明显变化的答案，展示下一轮问题跟着改变。
4. 展示需求 brief 卡片，点击“确认并开始”。
5. 马上换一个明确小任务：“把 README 里的 recieve 改对。” Agent 直接改，不弹窗。
6. 结尾只放一句：“会问很重要，知道什么时候不该问更重要。”

演示必须录真实 DSH 弹窗，不用 Figma 假界面。第 5 步是整个演示的关键，它证明这不是一个“每次强制填表”的插件。

## 发布顺序

1. 创建 `1052326311/dsh-ask-first` 公开仓库，推送当前代码，开启 CI。
2. 在 DSH `0.1.2-rc.1` 真实 Web 会话中录制上述 30 秒 GIF 和一张 brief 确认截图，放到 README 首屏。
3. 用同一模型对评测表每个场景至少重复 5 次，同时跑未安装插件的基线；公开对话和原始评分。
4. 发布 GitHub Release 和 `.tgz`，再发 npm；发布前更新 Changelog 日期。
5. 公开仓库满 1 天后向 `awesome-dsh-plugin` 提交收录，文案使用 [收录条目草案](awesome-dsh-plugin-entry.yml)。
6. 再发社区内容：先发对比 GIF，后发设计原则和 eval 数据，不在第一条里塞完所有技术细节。

## 建议跟踪的指标

- 安装后首次原生弹窗成功率。
- 从用户首句到 brief 批准的中位时间和问题数。
- 实现开始后，用户纠正方向的次数。
- 明确小任务上的无必要提问率。
- 确认卡中“修改 brief”与“继续问我”的使用比例。

优先降低“开工后才发现理解错了”，不要追求更多问题。

## 后续功能只按证据排序

- 如果用户经常想临时切换，再做会话级 Ask First 开关或命令。
- 如果模型经常未确认就写入，再研究基于可靠工具风险元数据的可选硬门禁；不用工具名黑名单猜风险。
- 如果用户需要跨会话交接，再增加明示开启的 brief 文件持久化；默认仍不落盘。
- 如果其他界面需要特化 brief review，向 DSH 提案新的原生 intent，不滥用 `plan-review`。
